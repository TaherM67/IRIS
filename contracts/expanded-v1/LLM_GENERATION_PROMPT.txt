IRIS SYNTHETIC DATA GENERATION AGREEMENT
Contract: iris-expanded-input-v1, version 1.0.0
Serving profile: iris_scenarios_20261109
Use the supplied JSON Schemas and control_catalogue_reference.json as normative.
Create fictional development data only. Do not claim clinical, operational,
expert-reviewed, or real-world security performance.

DELIVERABLES
1. asset_inventory.json: canonical UTF-8 JSON object; the asset schema applies.
2. risk_register.json: canonical UTF-8 JSON object; the risk schema applies.
3. siem_alerts.jsonl: one complete canonical event object per line; no JSON array.
For later supervised refinement also deliver:
4. training_labels.jsonl: offline annotations, one per exact prepared session.
Never embed offline labels, control targets or desired risk scores in files 1-3.
The fixed catalogue reference is provided by IRIS; do not generate a replacement.

RECOMMENDED METHOD
Prefer writing and executing a deterministic Python generator that writes all
files, rather than printing thousands of records into a chat response.
Use random seed 20261114 and include the generator source.
If code execution is unavailable, return the full runnable generator source.
Do not use ellipses, placeholders, partial JSON or truncated output.
Preserve a single ID registry while generating the three linked files.

REQUESTED NOMINAL DATASET
- 40 distinct fictional assets, with realistic and limited control_groups.
- Six current risk categories per asset: exactly 240 logical current risks.
- Give at least 8 assets and their 48 corresponding risks two historical versions.
  Keep one logical ID across versions and use distinct version IDs.
- Exactly 60 genuinely varied campaigns. Generate 3 sessions per class in each
  campaign: 60 x 3 x 7 = 1,260 source runs and prepared sessions.
- The seven offline classes are benign, credential_access, reconnaissance,
  malicious_execution, privilege_escalation, web_exploitation, data_exfiltration.
- Use fictional dates across both sides of the history-change boundary, such as
  October through early November 2026. No session may straddle that boundary.
- Vary observed counts and spacing, accounts, fictional external addresses,
  severity, business criticality, existing controls and implementation states.
  Criticality, likelihood and impact must be pre-existing values independent of
  the activity's true class. They must not be manufactured from the target.
- Make 36 of the 180 routine sessions benign lookalikes, and 216 of the 1,080
  attack sessions subtle/noisy variants: 20% difficult cases in each group.
  Do not make each class a unique protocol, severity, fixed count or constant
  flag pattern. A detector indicator is an observed signal, not ground truth.
- Event counts can vary by activity, for example 5-12 for routine activity,
  20-35 credential observations, 18-32 reconnaissance observations, 6-14 process
  observations, 4-10 privilege observations, 6-18 web observations and 5-12
  outbound observations. These are generation examples, not training labels
  encoded in runtime fields and not universal operational detection rules.
- Keep total alerts <= 50,000 and the alert file <= 20 MiB; keep each other
  operational file <= 5 MiB. Report the actual counts, never truncate to fit.

EXACT FORMAT AND SEMANTICS
- All required fields in the supplied schemas must be present. No extra keys.
  Integer fields use integer notation, for example 3 rather than 3.0.
  Use a JSON null only where the schema permits null. False and zero mean
  explicitly observed false/zero; they do not stand for an unknown measurement.
- Every generated source declares data_provenance = "synthetic"; each alert
  declares it separately.
- UTC timestamps end in Z. Histories are non-overlapping half-open intervals
  [valid_from, valid_to). recorded_at is the time the record became known.
- An event must have an asset snapshot valid AND known at its timestamp.
  Relevant risk versions must be valid and known at that same timestamp.
- Each active asset/category combination has one unambiguous registered risk.
- Supported event_family values: authentication, network, privilege, process, web.
- Supported protocol values: HTTPS, LOCAL, SSH, TCP. Preserve exact casing.
  Do not disguise UDP or another unsupported protocol as TCP/SSH. A broader
  vocabulary requires a new contract and an evaluated model profile.
- For inbound observations, destination_ip is the monitored asset's IP.
  For local or outbound observations, destination_ip is null. source_ip is
  the monitored asset for local/outbound events. remote_destination_ip is the
  remote recipient for outbound events, otherwise null. asset_id is explicit.
- Include bytes_sent and all six observed booleans:
  process_unsigned, privilege_change, web_attack_signal, sensitive_data_access,
  destination_untrusted, malicious_indicator.
  bytes_sent is per-event measurement, never a repeated whole-session total.
  Local process/privilege events have bytes_sent = 0.
- For each nominal session keep campaign_id, run_id, asset_id, account,
  source_ip and event_family constant. Keep its protocol consistent.
  Consecutive gaps are <= 60 seconds and the snapshot context stays fixed.
  Use a separate opaque run_id for a genuinely separate activity.
- Use unique stable event_id values. Remove redelivery duplicates from this
  clean dataset. Unknown assets, invalid timestamps and conflicting duplicates
  belong only in a separate negative-test bundle with expected diagnostics.
- sensor_healthy is true in the nominal healthy bundle. Do not relabel missing
  sensor evidence as healthy. Separate intentional unhealthy-sensor cases.
- Use actual observed ATT&CK IDs only when supported by the synthetic event.
  Standard examples are T1110 (credential access), T1046 (reconnaissance),
  T1059 (execution), T1068 (privilege escalation), T1190 (web exploitation),
  T1048 (exfiltration). Use only allowed catalogue IDs; no invented technique IDs.
- Routine activity normally has mitre_technique = null. Do not invent an attack
  technique to force a control recommendation. For the nominal balance above,
  up to 180 routine sessions can legitimately have no Model 2 technique context;
  this does not stop their Model 1 analysis.
- Risk membership arrays and registered technique links are explicit and
  versioned. Existing and planned control ID sets are disjoint.
- Select relevant controls from the supplied catalogue that match both the
  registered risk technique and the asset's applicability groups.
  Do not put all controls or all groups on every asset/risk.
- Use control_states only for registered existing/planned controls. Unknown
  implementation is "unknown", not an invented effectiveness percentage.
  Active exception IDs also belong to that same explicit membership.
- Do not supply predicted_class, scenario_class, label, ground_truth, target,
  recommended_control_ids, desired_priority, or any post-decision value in
  the operational files. Raw detector rule IDs are not truth annotations.

OFFLINE ANNOTATIONS
- Follow training_label.schema.json and include each source event exactly once.
  Each annotation's event_ids must equal exactly one prepared session.
- Each row records case_id, event_ids, campaign_id, run_id, template_group,
  scenario_class, label_source, review_status, label_verified, reviewer,
  recommended_control_ids, controls_reviewed, control_reviewer.
- For LLM output set label_source = "llm_synthetic", review_status = "unreviewed",
  label_verified = false, reviewer = null, controls_reviewed = false and
  control_reviewer = null. Do not let the generating LLM certify itself as an
  independent expert. Leave control target arrays empty if unsupported.
- template_group identifies a copied or derived base scenario. Do not rename
  a reused template to pretend it is independent. Similar copied sequences,
  same campaigns and identical observed feature vectors must not cross
  experimental roles. Provide genuinely varied behaviors and source stories.
- Runtime inference never reads this file. The seven-class training handoff
  does not use the older three-class train-three command.

ACCEPTANCE
From the updated IRIS repository, run:
  python tools/validate_inputs.py --input-dir PATH_TO_BUNDLE --out qualification.json
Correct every contract error and explain every remaining warning.
Then, without fitting a model, prepare the offline handoff:
  python tools/prepare_expanded_training.py --input-dir PATH_TO_BUNDLE --labels PATH_TO_BUNDLE/training_labels.jsonl --out NEW_REVIEW_DIRECTORY
The handoff keeps shared campaigns/templates/identical features together and
requires independent label review and adequate class support before fit readiness.
Finally run the isolated inference coverage check if the updated repository is
available. Do not change model weights, confidence thresholds, released status,
accounts, approvals, or local databases to obtain a better-looking score.
Return the files, generator source and validation reports. Never claim perfect
accuracy, independent expert validation or real-world control effectiveness.
